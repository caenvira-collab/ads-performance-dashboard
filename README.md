# Ads performance dashboard (Meta Ads x GoHighLevel)

A static, single-file HTML dashboard that joins ad spend from Meta Ads with lead outcomes from GoHighLevel (GHL), per ad, for several local-business accounts. In the original project there were 8 dental-clinic accounts. GHL is the source of truth for leads and Meta is the source of truth for spend. There is no backend: `dashboard.html` is generated by a few Python scripts and opened straight from disk.

This repository is a clean copy of a working internal project. It holds code and documentation only. It has no credentials, no client data and no real account identifiers:

- Client names are replaced by `<CODE> Clinic` (the short client codes such as `FCI` stay, because the code is keyed on them).
- Campaign ids and ad ids are fake (18 digits starting with `99`, with the same last three digits the scripts rely on).
- The data used in the demo is synthetic. It is generated by `tools/make_sample_data.py`, not derived from real data.

Everything here runs on the Python standard library. It was tested with Python 3.13.4 (`zoneinfo` needs 3.9 or newer).

## How the data flows

```text
Meta Ads, per ad and per day --- meta_pull_merge.py ---> meta_daily_{C}.json --+
GHL contacts API ------------- fetch_ghl.py -----------> ghl_{C}.json ---------+--> build_perf.py --> perf_{C}.json
Meta active-ad status -------- ad_status.py -----------> ad_status.json -------+            |
                                                                                            v
                                         dashboard.template.html + perf files --> rebuild_dashboard.py --> dashboard.html
                                         registros.json + notas_originales.csv --> pruebas/construir.py --> pruebas/datos.js
```

Attribution, as implemented in `build_perf.py`:

- Every ad name starts with a code `YY.MM.DD-NN` (for example `26.11.12-02`). The code is the join key between Meta and GHL.
- A campaign line ("bucket", for example `T1D`, `ThinArch`, `Lower Funnel`) is resolved for each GHL contact first from its ad code, cross-checked against the Meta data, and only then from the contact's `source` text.
- The per-ad metrics come from GHL tags: unique leads, good leads, better leads, confirmed appointments, shows, clients, and won revenue.
- `docs/CONTEXTO_SESION.md` (Spanish) explains the attribution rules and the incidents that shaped them.

## Files

| File | Role |
|---|---|
| `paso0_actualizacion.py` | Pre-flight check, backup of the data files, prints the Meta date range to pull |
| `fetch_ghl.py` | Pulls and refreshes GHL contacts (30-day refresh window) into `ghl_{C}.json` |
| `meta_pull_merge.py` | Merges saved Meta answers into `meta_daily_{C}.json` (report first, `--apply` to write) |
| `ad_status.py` | Writes `ad_status.json`, the ids of the ads Meta reports as ACTIVE |
| `build_perf.py` | Attribution engine and the account-specific campaign maps |
| `rebuild_dashboard.py` | Embeds the perf files into `dashboard.template.html` and writes `dashboard.html` |
| `reconstruir.py` | Runs the perf rebuild, `rebuild_dashboard.py` and `pruebas/construir.py` in one command |
| `audit_missing_spend.py` | Health check on `meta_daily_{C}.json` |
| `backup_datos.py` | Backup and restore of the data files |
| `pruebas/` | Test-history page: `construir.py` builds `datos.js`, `index.html` is the UI |
| `tools/make_sample_data.py` | Synthetic data generator |
| `docs/` | The three working documents, in Spanish |

## Demo run with synthetic data

```bash
python3 tools/make_sample_data.py --pull    # writes git-ignored data files and meta_results/
python3 reconstruir.py                      # perf files, dashboard.html, pruebas/datos.js
open dashboard.html                         # any browser works

# Optional: replay a pull the way a real update does
export META_RESULTS_GLOB="meta_results/mcp-*-ads_get_ad_entities-*.txt"
python3 meta_pull_merge.py 1000             # report only
python3 meta_pull_merge.py 1000 --apply     # merge into meta_daily_*.json
python3 ad_status.py 2000                   # active ads
python3 reconstruir.py
python3 paso0_actualizacion.py              # backup, then prints the date range to pull next
python3 audit_missing_spend.py
```

This exact sequence was run on a copy of this repository before it was published. The two MDIC campaigns that print `CAMPANAS SIN AREA` are expected: they stand for the old paused campaigns that have no Inner/Outer area.

### Shape of the Meta files

`meta_pull_merge.py` and `ad_status.py` read one JSON file per pull. The file holds a key `ad_entities` whose value is a JSON-encoded list of rows with `id`, `campaign_id`, `name`, `amount_spent` (a number, a string, or an object with `value`), `clicks`, `impressions` and `date_start`. The status pull rows carry `effective_status` instead of spend. An optional `pagination.next_cursor` makes the scripts warn that the list is incomplete. The number in the file name (`...-ads_get_ad_entities-<number>.txt`) orders the rounds, and each script takes the smallest number of a round as its argument. `tools/make_sample_data.py --pull` writes examples of both kinds.

## Using it with real accounts

1. `cp clients.example.json clients.json` and fill in the GHL location id, the GHL private-integration token, the Meta ad account id and the time zone of each GHL location. `clients.json` is git-ignored. Never commit it.
2. Replace the campaign maps: `CAMP_MAPS`, `WLA_CAMP_MAP`, `CAMP_AREA` and `CAMP_TIPO` in `build_perf.py`, and the second copy of `CAMP_MAPS` in `fetch_ghl.py`. They contain fake ids in this repository.
3. Replace the client routing in `meta_pull_merge.py` and `ad_status.py` (see "Found while preparing this copy").
4. Feed the two Meta scripts with real pulls, or write a client that produces the same file shape (see above). Set `META_RESULTS_GLOB` to where those files live.
5. Follow `docs/PROCEDIMIENTO_ACTUALIZACION.md` for the update order.

## What an engineer cannot replicate from the files alone

This list describes the original project folder, before this copy was prepared. Every item below refers to the Claude session that ran the updates in the original project.

- **Meta data:** it is pulled through Claude's Meta connector, and the project has no code of its own for that. `meta_pull_merge.py` and `ad_status.py` read the files that Claude saves in `~/.claude/projects/.../tool-results/`, named `mcp-...-ads_get_ad_entities-<number>.txt`. The engineer would have to write their own client against the Meta API and replace those two scripts. The details of that API were not verified.
- **Verifications 1 and 2:** they do not exist as scripts. The Claude session writes them at each run, and verification 1 is transcribed by hand from Meta's responses. They would have to be saved as files.
- **Hard-coded paths:** `/Volumes/<disk>` appears in 14 files and `/Users/<user>` in 3.
- **Mappings specific to these 8 accounts:** `CAMP_MAPS`, `CAMP_AREA` and `CAMP_TIPO` in `build_perf.py`, plus the ad naming convention (codes such as `26.11.12-02`).
- **The procedure:** `PROCEDIMIENTO_ACTUALIZACION.md` is written for a Claude session (for example "one command per Bash call"), and a person would have to adapt it.

### Status in this copy

- Hard-coded paths: removed from the scripts that are included. Each script resolves the project folder from its own location.
- Meta files: `META_RESULTS_GLOB` lets `meta_pull_merge.py` and `ad_status.py` read from any folder. The default is still the Claude path. A client for the Meta API is not included.
- Campaign maps: present, with fake ids. They still have to be replaced.
- Verifications 1 and 2: still not scripts. Step 7 of `docs/PROCEDIMIENTO_ACTUALIZACION.md` defines them.
- Procedure: only sanitized (names, ids, personal references). It is still written for a Claude session and is in Spanish.

### Found while preparing this copy

- **Client routing by campaign id suffix.** `SUF` in `meta_pull_merge.py` and `ad_status.py` maps the last 3 digits of a `campaign_id` to a client code. It worked for the original 8 ad accounts and has to be replaced for any other account.
- **Duplicated maps.** `CAMP_MAPS` and `SRC_BUCKET` exist in both `fetch_ghl.py` and `build_perf.py` and are kept in sync by hand. `docs/CONTEXTO_SESION.md` lists every place a new campaign line has to be added.
- **Hard-coded colors.** `CAMP_COLORS` in `dashboard.template.html` lists the campaign lines. A line missing there is skipped by the projection and traffic-light panels.
- **Dead button.** The "Actualizar datos" button in the template calls `http://localhost:8081/rebuild`. The server it expects (`server.py`) is not included because it was already marked legacy.
- **Account-specific rules in code.** `EXCLUSIVOS` in `pruebas/construir.py` encodes one creative rule of the original accounts (a callout allowed in a single campaign). Remove or replace it.
- **GHL fetch not exercised.** `fetch_ghl.py` compiles but was not run against GHL here, because that needs real credentials.

## Changes against the original project

- Paths resolve from the script location instead of a fixed disk path.
- `rebuild_dashboard.py` reads `dashboard.template.html` and writes `dashboard.html`, so generated data never lands in a tracked file. The template is the original page with the embedded data blobs emptied.
- `META_RESULTS_GLOB` override in the two Meta scripts.
- Client names, campaign ids and account identifiers replaced as described at the top.
- The three documents in `docs/` lost the sections that were specific to the assistant session, and their names, ids and dollar amounts were scrubbed. They stay in Spanish.
